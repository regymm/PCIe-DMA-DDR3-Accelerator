### Project Overview

This section outlines the inception of the project, its objectives, and the team structure. The project was developed by Our-team, a group of six members, as part of their graduation project during their bachelor's year. Our-team is known as Electronic Aliens. The project aims to assist drivers in automating the cruise by creating a pure hardware system capable of efficiently supporting autonomous driving. By excluding software from the computation process, the team seeks to optimize the system and gain hands-on experience with hardware. The system includes an AI block for detecting potential objects during the cruise, drawing inspiration from examples such as Tesla cars. The goal is to deliver an edge-computing pure hardware device, utilizing either FPGA or ASIC. The system does not employ any software, enabling autonomous driving and deploying AI on hardware.

### Literature Review

This section reviews the algorithms explored by Our-team before the project implementation. Our-team decided to use an AI algorithm for autonomous vehicles, specifically deploying it on FPGA. Research was conducted to find the most suitable AI algorithm. Convolutional Neural Networks (CNN) are known for their efficiency in Computer Vision applications. R-CNN, a regional CNN, is known for producing accurate outputs but with high latency. After thorough research, Our-team concluded that the YOLO network would be more efficient for their application. YOLO enables low latency inference and satisfactory accuracy, with the abbreviation YOLO standing for "You Only Look Once." Choosing a specific version of YOLO was challenging due to its complexity and the need for a hardware-friendly implementation.

### Target Hardware

This section discusses the hardware used and who provided it. Our-team decided to implement the system on the ZCU102, which is available from the Electronics Research Institute (ERI). ERI enables the use of ZCU102 for Our-team. ZCU102 is known for its high capabilities and being a Multi-Processor System-on-Chip (MPSoC).
### System Overview
Our team has decided to utilize only the Programmable Logic (PL) part of the ZCU102. The PL represents the FPGA side of the System on Chip (SoC). This decision is made because our team has excluded any software from the computation process. The system is composed of two pure hardware blocks, meaning no software is involved in the entire inference process.

#### Block Diagram
The system consists of an accelerator and a post-processing block. The system also includes a source of AXI-stream data and a source for the inference output in the form of AXI-stream. The system is entirely composed of hardware modules on the FPGA.

#### AXI-Stream Details
The AXI-Stream data represents the input image, which is a set of 416 x 416 pixels. This input image models a road view. The AXI-Stream is used due to its efficiency in image processing applications and low communication overhead. It is a standard interface used by most Xilinx IPs.

Our team has chosen AXI-Stream as the system's input and output interface. The inference output consists of 13 row_det signals and a detect_valid bit. Each row_det signal represents a 13 x 13 grid, with each bit representing 32 x 32 pixels. The detect_valid bit ensures that the receiving block only catches valid predictions, enhancing safety and response speed.

#### System Details
The accelerator is responsible for the neural network, while the post-processing block processes the raw output of the neural network to derive the final inference results. The used YOLO model is called LPYOLO, which is a variant of YOLO. The LPYOLO model replaces the sigmoid function with hard tanh for hardware compatibility. This model was developed by Sefa Burak in 2022 and was initially designed for face detection but has been adapted for car detection. Our team has trained LPYOLO to serve the car detection purpose. The used dataset is a cars detection dataset published by a user on Kaggle. The replacement of sigmoid with hard tanh makes the model more hardware-friendly.

The accelerator is called streamingdataflowpartition and is generated by the FINN Framework. FINN Framework is a hardware IP generation framework created by Xilinx Research Lab and is completely open-source. The FINN flow consists of six stages, as detailed in the reference provided.

The post-processing module is called yolo_post and was implemented using Verilog, which supports higher throughput and better resource control.

#### Raw Detection Bytes
The raw detection bytes come from the accelerator, which supplies the post-processing block with the raw detection results of the neural network computations.
### YOLO Post-Processing Action and Processing of Raw Detection Bytes

The YOLO post-processing action involves processing the raw detection bytes. Specifically, the third byte of the raw detection bytes represents the probability of the class and the objectness scores. The NN output contains three anchor boxes, each generating six bytes. The last two bytes of these six bytes represent the probability of the class and objectness scores. The class and objectness scores are represented by two bytes for each anchor box. The class and objectness scores determine the presence of cars when multiplied together. These scores represent probability, and to obtain the final result, they are multiplied together. The multiplication implies no floating-point operations.

The system considers three anchor boxes for safety purposes. If only one anchor box senses a car, the system still reports the presence of a car.

### Implementation

#### Detailed Steps of Implementation

This section discusses the detailed steps of implementing the system. Jupyter Notebooks are used for most of the implementation flow, and Colab Cloud is used for training and exporting. Colab Cloud is provisioned by Google. After training the NN, the trained model is derived to produce a QONNX file. The QONNX file represents the quantized NN. The QONNX file is delivered to FINN for transformations. The transformations involve eliminating floating-point operations and converting NN layers to hardware conversions. FINN Framework enables transformations checking, and transformations checking should precede IP generation. The parallelism degree of the accelerator is determined by configurations decided by the designer, and the accelerator clock frequency is also determined by the designer. For our system, we set the frequency to 150 MHz, which should be sufficient for real-time calculations. The FINN flow involves running Jupyter Notebooks on a local host. Post-processing is handled by YOLO_post, which involves no floating-point operations. YOLO_post makes use of Verilog functions for tidying the code.

### Inference Results

#### Visualization of Hardware Results

For visualizing the hardware results, a PYNQ Jupyter Notebook was used. This implies implementing the accelerator on the PYNQ-Z2 besides the main board, which is ZCU102. Testing on the PYNQ-Z2 uses Xilinx AXI DMA for sending test images. Designing on the PYNQ-Z2 implies a lower clock frequency due to resource limitations. The clock frequency on the PYNQ-Z2 has a value of 100 MHz. The system generates high-valued bits for grids containing cars, leading to reliable inference results. The system was published by our team in the IEEE ICECS25 Proceedings. The system successfully handles real-time processing. The inference rate has a value of 67 FPS on ZCU102 and 18 FPS on PYNQ-Z2. The system proved its capability in autonomous vehicle applications.
